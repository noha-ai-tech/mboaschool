# 02 — Ressources humaines (Phases 2, 3, 5)

## Module Personnel (Phase 2)

Nouveau menu `/pro/personnel`, ajouté à la navigation Pro existante (`src/app/pro/layout.tsx`, un seul lien
ajouté, rien retiré). Liste groupée par catégorie, dans cet ordre d'affichage : Direction, Enseignants,
Personnel administratif, Personnel de soutien.

**Extensibilité** : `staff_category` est un enum à 4 valeurs (`teacher`/`admin`/`direction`/`support`) ; ajouter
une 5ᵉ catégorie ne nécessite qu'une valeur d'enum supplémentaire et une entrée dans `CATEGORY_LABELS`
(`src/app/pro/personnel/page.tsx`), pas une refonte de table.

## Table `staff_members` — registre RH généralisé

Voir `supabase/migrations/0009_pro_hr_foundation.sql` pour le schéma complet. Point de conception central :
**`staff_members` s'ajoute à côté de `enseignants`, ne le remplace pas.** Pour le personnel enseignant,
`staff_members.enseignant_id` pointe vers la ligne `enseignants` existante — matières, emplois du temps,
pointage continuent de fonctionner exactement comme avant cette mission, via la table `enseignants` inchangée.
`staff_members` est la couche RH (statut, contrat, documents, rôle organisationnel) qui manquait.

Pour le personnel non-enseignant (`category != 'teacher'`), `enseignant_id` reste `null` — ces personnes
n'apparaissent jamais dans `/pro/enseignants`, `/pro/matieres` ni les emplois du temps, cohérent avec le fait
qu'elles n'enseignent pas.

**Rétro-compatibilité** : la migration rétro-remplit une ligne `staff_members` pour chaque `enseignants`
existant (`category='teacher'`, `role='enseignant'`) — le module Personnel affiche donc immédiatement le
personnel enseignant déjà créé, sans ressaisie, dès l'exécution de la migration.

## Fiche complète (Phase 3)

`/pro/personnel/[id]` affiche : informations personnelles (nom/prénom/photo), coordonnées (email/téléphone),
matières (si enseignant, lues depuis `enseignant_matieres` existant — pas dupliquées), statut (actif/inactif),
date d'entrée, type de contrat (temps plein/partiel/vacataire), documents, et les actions d'accès (Phase 4).

**Photo** : le champ `photo_url` existe dans le schéma, mais **aucun formulaire d'upload de photo n'a été
construit** dans cette mission (l'upload de logo pour l'établissement n'existe pas non plus — voir
`docs/dashboard/03_WIDGETS.md`, "Centre documentaire") — la fiche affiche la photo si elle existe (initiales en
avatar par défaut sinon), cohérent avec "ne pas développer les fonctionnalités absentes".

## Organisation — sections (Phase 5)

Structure préparée, interface minimale volontairement : table `sections` (`etablissement_id`, `nom`, `type`,
`responsable_staff_member_id`), et `classes.section_id` (nullable, `on delete set null` — une classe existante
reste valide sans section assignée). Relation complète : `establishments → sections → classes → enseignants →
matieres` (via `enseignant_matieres`), exactement la hiérarchie demandée par la mission.

**Aucune interface de gestion des sections n'a été construite** — la mission demande explicitement "ne pas
développer les emplois du temps, préparer simplement la structure" pour cette phase ; le schéma est prêt, une
interface (formulaire de création de section, assignation d'un responsable, rattachement des classes) reste à
construire dans une mission dédiée une fois la structure validée par le fondateur (notamment la distinction
maternelle/primaire/secondaire général/technique déjà évoquée dans `CLAUDE_CONTEXT.md`).
